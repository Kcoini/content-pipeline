# wordpress_blog 프롬프트

## platform 정의 (핵심)
wordpress_blog는 **SEO(검색 유입) + AEO(직접 답변) + GEO(생성형 AI 검색
이해성) + E-E-A-T(신뢰성)를 함께 고려한, WordPress 게시용 문제 해결형
블로그 글**이다. 단순히 "긴 SEO형 글"이 아니다. 검색자가 가진 구체적
질문을 해결하는 글이며, 독자는 이 글을 읽은 뒤 **자신이 대상인지,
어떤 조건을 충족해야 하는지, 어떤 절차를 밟아야 하는지, 무엇을 주의해야
하는지, 다음에 무엇을 하면 되는지**를 스스로 판단할 수 있어야 한다.

**wordpress_blog는 article rewrite가 아니라 source-grounded blog
reconstruction이다.** article은 topic context(주제/맥락/기존 관점을
파악하는 용도)이고, article_sources/source summaries가 factual
basis(사실/조건/절차/수치/기간/기관명/예외/주의점/FAQ의 주된 근거)다.

## article과 sources의 역할 분리 (반드시 지킨다)
- **article**(title/content 요약/mode): 주제, 기본 맥락, 핵심 관점,
  기존에 이미 생성된 SEO metadata(있다면)를 파악하는 용도로만
  참고한다. **article 문장을 단순 확장하거나, article의 짧은 요약을
  길게 늘리는 방식으로 쓰지 않는다.** article 원문 순서를 그대로
  따라가지 않는다.
- **article_sources / source summaries**: 실제 사실적 근거다 —
  조건, 절차, 수치, 기간, 기관명, 예외, 주의점, FAQ는 여기서 가져온다.
  source별 내용을 단순 나열하지 않고, source에서 확인된 사실을
  바탕으로 **독자 관점의 새로운 구조**를 만든다.
- **wordpress_blog 본문**: article을 다시 쓰는 것이 아니라, sources에
  근거해 독자 문제 해결형 블로그 글로 **새로 구성**한다. 검색 의도,
  topicType, SEO/AEO/GEO/E-E-A-T 기준에 맞게 재배열한다. 출처에 없는
  정보는 만들지 않는다.

## 출처(sources) 충분성에 따른 처리 — 3단계 모드
usable source(요약 또는 key_points가 있는 출처) 개수에 따라 아래 3가지
모드 중 하나로 작성한다(`lib/social/wordpress-blog-source-mode.ts`의
분류와 동일):

- **no_source(usable 0개)**: wordpress_blog 생성 자체가 시스템에서
  차단된다(이 프롬프트가 호출되는 시점에는 이미 usable source가 1개
  이상이라는 뜻이다). 혹시라도 이 모드로 판단되면 본문을 무리하게
  만들지 말고 "확인된 정보가 부족합니다"를 명확히 하며, 확인 필요
  사항/공식 확인 항목/독자 체크리스트 중심으로 짧고 정직하게
  구성한다. `missingInformationWarnings`에 그 사실을 남긴다.
- **single_source_mode(usable 1개)**: 생성은 허용되지만, 출처가
  하나뿐이라는 한계를 명확히 인지하고 작성한다. 아래
  "single_source_mode 작성 규칙" 섹션을 따른다.
- **normal_source_grounded_mode(usable 2개 이상)**: 아래 "본문 길이/깊이
  기준"의 목표 길이(2,500~4,000자)를 정상적으로 목표로 삼아 source 기반
  재구성을 수행한다.

user prompt에 `글쓰기 모드: single_source_mode` 또는 `글쓰기 모드:
normal_source_grounded_mode`가 명시되어 전달되므로, 그 지시를 그대로
따른다. source summary/key points가 비어 있으면, article만으로 그
공백을 채우지 않는다 — 부족한 부분은 "출처 추가 후 재생성을
권장합니다"로 남긴다.

## single_source_mode 작성 규칙 (usable source 1개일 때 반드시 지킨다)
- **article**은 topic context(주제/맥락 파악용)로만 쓴다. 사실적 근거로
  쓰지 않는다.
- **단일 출처의 summary/key points**만 factual basis(조건/절차/수치/
  기간/기관명/예외/FAQ의 근거)로 쓴다.
- 출처를 그대로 요약(verbatim summarizing)하지 않는다 — 반드시 독자
  문제 해결 순서로 재구성한다.
- 출처에 없는 조건/금액/신청 기간/기관명/절차를 추측하거나 지어내지
  않는다.
- 출처에 없는 정보는 "확인 필요 사항" 섹션에 명확히 분리하고, "공식
  안내에서 확인할 것"으로 안내한다.
- **비교할 대상이 실제로 출처에 없다면 비교표를 억지로 만들지
  않는다** — 대신 체크리스트로 대체한다.
- FAQ는 반드시 출처에 근거한 질문만 포함한다(출처에 없는 질문을
  지어내지 않는다).

### single_source_mode 권장 본문 구조
1. 도입부
2. 먼저 결론(핵심만 정리하면)
3. 단일 출처 핵심 내용
4. 대상자/조건
5. 신청/확인 방법
6. 내 상황별로 확인할 것
7. 주의점 / 확인 필요 사항
8. FAQ (출처 근거 질문만)
9. 최종 체크리스트
10. 참고자료(출처)

## 본문 길이/깊이 기준 (중요)
- `preferredLength=long`, 시스템이 허용하는 절대 범위는 최소 1,800자
  ~ 최대 8,000자(`lib/social/platform-writing-config.ts`의
  `wordpress_blog.minLength`/`maxLength`)이지만, **이것은 안전선이지
  목표가 아니다.**
- **normal_source_grounded_mode(usable source 2개 이상) 목표 길이**:
  한국어 기준 **2,500~4,000자**, 시스템이 허용하는 절대 최소는
  **1,800자**(`lib/social/social-quality-gate.ts`의
  `WORDPRESS_BLOG_MIN_ACCEPTABLE_BODY_LENGTH`).
- **single_source_mode(usable source 1개) 목표 길이**: 출처가 하나뿐인
  한계를 감안해 **1,800~3,000자**로 완화하며, 시스템이 허용하는 절대
  최소는 **1,500자**(`WORDPRESS_BLOG_SINGLE_SOURCE_MIN_ACCEPTABLE_BODY_LENGTH`).
  **이 최소 길이를 채우기 위해 출처에 없는 내용을 지어내지 않는다** —
  정직하게 짧은 글이 지어낸 긴 글보다 낫다.
- 800자·1,200자는 "정상"이 아니라 "위험 신호"다 — 그 정도로 짧다면
  article 개요만 우려낸 얕은 글일 가능성이 크다.
- `seoTitle`/`metaDescription`/`answerSummary`/`eeatNotes`/
  `geoSummary`/`structuredDataSuggestions`/`titleCandidates` 같은
  metadata는 **본문(post_body) 길이에 포함하지 않는다** — 길이 기준은
  오직 `post_body` 자체를 말한다.
- 길이는 독자 판단에 필요한 설명·비교·체크리스트·FAQ·주의점으로
  채운다. **길이를 늘리기 위해 출처에 없는 사실을 지어내지 않는다.**
  sources가 부족해서 짧아지는 것은 정상이다 — 그럴 때는 무리하게
  채우지 말고 "확인 필요 사항"으로 정직하게 남긴다.

## 본문 구조 형식 (반드시 지킨다 — quality gate가 자동으로 검사한다)
- **`post_body`는 반드시 markdown h2/h3(`## `, `### `) 구조를 가져야
  한다.** 소제목 없이 문단만 이어 쓰지 않는다.
- **source key points를 "A / B / C"처럼 한 문단에 `/`로 이어 붙이지
  않는다.** key points는 목록(`- `)/표/조건 정리/FAQ/주의점 섹션으로
  재구성한다 — "주요 포인트: ..." 한 줄 요약으로 대체하지 않는다.
- 이 두 가지를 지키지 않으면 article summary/excerpt를 그대로 옮긴
  것처럼 보이고, `lib/social/social-quality-gate.ts`의
  `wordpress_blog_heading_structure`/`wordpress_blog_no_slash_joined_points`
  검사가 `fail`(needs_revision)로 처리한다.

## 허용 필드
`post_title`(필수), `post_body`(필수), `excerpt`(선택), `hashtags`는
지원하지 않음(WordPress는 카테고리/태그를 별도 필드로 관리).

## 0단계. 본문을 쓰기 전에 반드시 contentBrief를 먼저 만든다
본문을 바로 쓰지 말고, 아래 항목을 먼저 내부적으로 정리한 뒤 그 결과를
본문 작성에 반영한다. contentBrief 자체를 최종 사용자에게 그대로
노출할 필요는 없지만(즉 별도 필드로 출력하지 않아도 된다), **이
정리 없이 바로 본문을 작성하지 않는다.**

contentBrief 항목:
- 이 글의 핵심 질문(독자가 검색창에 입력했을 법한 질문)
- 독자의 검색 의도(searchIntent)
- 독자가 가장 먼저 알고 싶은 답(초반 결론이 될 내용)
- 글의 중심 관점(무엇을 기준으로 정보를 재구성할지)
- topicType(아래 "topicType별 구조" 참고)
- 반드시 포함할, 출처에 실제로 있는 정보
- 출처가 부족해서 단정하면 안 되는 정보(추측하지 않고 "확인 필요"로
  남길 항목)
- SEO/AEO/GEO/E-E-A-T를 각각 어떻게 반영할지
- 최종 글의 섹션 구성
- 예상되는 주의점/caveats
- 사용할 sources(어떤 출처를 어떤 목적으로 쓸지)
- 사용하지 않을 sources와 이유(관련 없음/신뢰도 낮음/중복 등)
- article에서 참고할 부분(주제/맥락)과 참고하지 않을 부분(구체적
  사실은 article이 아니라 sources에서 가져온다)

## topicType 판단과 구조 선택
article 내용을 보고 topicType을 하나 판단하고, 그에 맞는 구조를
따른다. **모든 섹션을 기계적으로 다 넣지 않는다** — 출처에 근거가
없는 섹션은 생략하거나 "확인 필요"로 짧게 처리한다.

- **policy_support**(지원금/복지/제도 안내): 도입부 → 먼저 결론 →
  대상자 → 조건 → 지원 내용 → 신청 방법 → 주의점 → FAQ → 공식 확인
  필요 사항
- **how_to**(신청 방법/절차 안내): 도입부 → 먼저 결론 → 준비 전 확인할
  것 → 단계별 절차 → 필요 서류/준비물 → 실수하기 쉬운 부분 → FAQ →
  최종 체크리스트
- **comparison**(제도·상품·조건 비교): 도입부 → 먼저 결론 → 비교
  기준 → 비교표 → 상황별 판단 기준 → 주의점 → FAQ → 최종 요약
- **explainer**(이슈 해설): 도입부 → 먼저 결론 → 배경 → 핵심 쟁점 →
  독자에게 미치는 의미 → 확인된 사실과 해석 구분 → 주의점 → FAQ
- **checklist**(준비물·조건 확인): 도입부 → 먼저 결론 → 체크리스트 →
  항목별 설명 → 놓치기 쉬운 부분 → FAQ → 최종 확인 사항
- **update_news**(최신 변화 정리): 도입부 → 먼저 결론 → 현재 확인된
  변화 → 바뀐 점 → 아직 확인이 필요한 점 → 독자가 해야 할 일 → FAQ

## 권장 본문 구조 (기본형)
topicType 구조가 애매하면 아래 기본 구조를 따른다:

1. 도입부
2. 먼저 결론(또는 핵심만 정리하면)
3. 핵심 요약 박스
4. 대상자/조건 정리
5. 핵심 정보 설명
6. 신청/확인 절차 또는 판단 기준
7. 내 상황별로 확인할 것
8. 비교표 또는 체크리스트
9. 주의점과 예외
10. FAQ
11. 최종 요약
12. 참고자료/출처

글의 흐름은 **article 원문 순서가 아니라 독자의 문제 해결 순서**를
따른다. 출처별 내용을 나열하지 않는다.

## 비교표(table) 작성 규칙 (중요)
지원정책/조건 비교표는 **"핵심 비교 요약" 용도로만** 사용한다 —
표 자체가 모든 정보를 담는 문서가 되어서는 안 된다.

- **긴 설명을 표 셀에 그대로 넣지 않는다.** 각 셀은 **1~2문장** 또는
  **bullet 2~3개 이내**로 제한한다(예: `이자 0.2%<br>대출잔액 3억
  이내`처럼 `<br>`로 짧게 나열하는 것은 허용하지만, 문단 수준의 설명을
  넣지 않는다).
- **긴 설명/예외/주의사항은 표 셀이 아니라 표 아래 본문 섹션으로
  분리한다**(예: "## 지원 금액과 조건 정리", "## 주의사항" 같은 별도
  섹션에서 자세히 설명한다). 표는 그 요약만 보여준다.
- 신청 기간/조건이 사업마다 달라 "별도 공지 확인 필요"가 반복되면,
  신청 기한 열 대신 **비고 열**을 따로 만들어 그 문구를 몰아서 담는
  것도 허용한다(신청 기한 열이 의미 없이 반복되는 것을 피한다).
- WordPress 전송 시 표는 자동으로 h2/h3와 같은 수준의 가독성 있는
  HTML로 변환되고(border/padding/열 너비/모바일 스크롤 대응 등),
  markdown 문법(`##`, `| 표 |`)이 WordPress 공개 화면에 그대로
  노출되지 않는다 — 다만 이 변환은 **표 형태(구분/대상/지원 내용/
  신청 기한 등)를 유지할 때만** 정상 동작하므로, 표 구조 자체는
  markdown 표 문법(`| ... | ... |`, 구분줄 `|---|---|`)을 정확히
  지켜서 작성한다.
- 표의 열 개수는 되도록 4개(예: 구분/대상/지원 내용/신청 기한 또는
  비고)를 넘지 않게 한다 — 열이 많아지면 모바일 화면에서 읽기
  어려워진다.

## SEO 기준
- 검색 의도(searchIntent)에 맞는 제목, 소제목, 본문 구조를 만든다.
- `seoTitle`(60자 이내), `metaDescription`(160자 이내), `targetKeyword`,
  `secondaryKeywords`를 생성한다.
- `targetKeyword`는 본문 초반과 주요 섹션에 자연스럽게 반영하되,
  **반복적으로 억지 삽입(keyword stuffing)하지 않는다.**
- h2/h3 구조를 사용해 검색자가 원하는 정보를 빠르게 찾게 한다.
- 비교표, 체크리스트, FAQ 등 체류시간을 높이는 구조를 사용한다.
- `seoTitle`은 클릭bait이 아니라 검색 의도와 핵심 정보를 반영한다.
- `metaDescription`은 독자가 이 글에서 무엇을 얻는지 분명히 알려준다.

## AEO 기준 (직접 답변)
- 독자의 질문에 **도입부 바로 뒤**에서 직접 답한다 — "먼저 결론부터
  보면" 또는 "핵심만 정리하면" 섹션을 둔다.
- `answerSummary`(2~4문장)는 metadata로만 만들지 말고, 본문 초반의
  이 섹션에도 자연스럽게(딱딱한 AI 답변처럼 보이지 않게) 반영한다.
- FAQ는 실제 본문 내용과 출처에 근거한 질문만 포함한다(근거 없는
  질문을 지어내지 않는다).
- 질문형 소제목을 적절히 사용하고, 답변은 짧고 명확하게 쓴다.
- 독자가 글을 끝까지 읽지 않아도 핵심 답을 먼저 알 수 있어야 한다.

## GEO 기준 (생성형 AI 검색 이해성)
- `geoSummary`(`{ directAnswer, keyFacts: [], caveats: [] }`)를
  metadata뿐 아니라 본문 구조에도 반영한다.
  - `directAnswer` → 본문 초반 "먼저 결론" 섹션과 연결한다.
  - `keyFacts` → 핵심 요약 박스 또는 "확인된 핵심 사실"에 반영하되,
    **출처에서 확인된 사실만** 사용한다(없으면 빈 배열).
  - `caveats` → "주의할 점"/"확인 필요 사항"/"예외" 섹션에 반영하며,
    조건·기간처럼 바뀔 수 있는 정보는 caveats로 분리한다.
- 출처에서 확인된 사실과 작성자의 해석을 문장 단위로 구분한다.
- AI가 요약하거나 인용하기 쉬운, 명확하고 짧은 문장 구조를 쓴다.
- **AI 검색 노출을 보장하는 표현은 절대 쓰지 않는다**("AI 검색에
  노출됩니다", "AI가 이 글을 인용할 것입니다", "검색 상위 노출 보장"
  같은 문구 금지).

## E-E-A-T 기준 (Experience/Expertise/Authoritativeness/Trustworthiness)
네 가지를 **각각 구분해서** 반영한다 — 하나로 뭉뚱그리지 않는다.

- **Experience**: 독자의 실제 상황을 이해하고, 독자가 겪을 수 있는
  판단 상황을 구체적으로 설명한다. **단, 작성자 개인의 경험이나 실제
  체험담·사용 후기를 지어내지 않는다.**
- **Expertise**: 제도·조건·절차·예외·주의점을 구조적으로 설명한다.
  복잡한 정보를 독자가 이해하고 판단할 수 있게 정리한다(단순 요약이
  아니라 판단 가능한 설명).
- **Authoritativeness**: 공식 기관, 원문 출처, 신뢰할 수 있는 자료를
  중심으로 설명한다. 출처가 불분명한 정보는 권위 있는 사실처럼 쓰지
  않는다.
- **Trustworthiness**: 확인된 사실과 해석을 구분하고, 변경 가능성이나
  확인 필요 사항을 명확히 표시한다. 독자가 스스로 확인해야 할 부분을
  숨기지 않는다.

금지:
- "전문가가 추천합니다"처럼 근거 없는 권위 표현
- 실제 사용 후기·체험담을 지어내는 것
- 공식 기관이 확인하지 않은 내용을 공식 정보처럼 쓰는 것
- 출처에 없는 수치·조건·신청 기간·기관명을 단정하는 것

---

## searchIntent 반영 규칙
`searchIntent`를 생성한 뒤 본문 구조에 반드시 반영한다(metadata로만
남기지 않는다):

- **신청 방법**: 대상자, 조건, 필요 서류, 신청 절차, 주의점 중심.
- **제도 비교**: 대상, 지원 내용, 차이점, 어떤 사람이 어떤 제도를
  봐야 하는지 중심.
- **조건 확인**: 대상 여부, 소득/연령/지역/기간 등 조건을 먼저 정리.
- **비용/금액 확인**: 지원 금액, 산정 기준, 확인 필요 사항 중심.
- **최신 정보 확인**: 현재 확인된 정보, 변경 가능성, 공식 확인이
  필요한 부분을 분리.

## 독자 상황별 판단 섹션
가능하면 "내 상황별로 확인할 것" 섹션을 둔다 — 독자가 자신의 상황에
따라 어떤 조건/절차/주의점을 먼저 봐야 하는지 판단하게 돕는다(예:
"신혼부부라면 먼저 확인할 것", "청년이라면 먼저 확인할 것", "해당되지
않을 수 있는 경우"). **출처에 근거가 없으면 구체 조건을 임의로 만들지
않는다** — 정보가 부족하면 "공식 안내에서 확인해야 합니다"라고 쓴다.

## 도입부 규칙
필수 조건:
- 첫 3~5문장 안에 독자의 상황과 핵심 결론을 제시한다.
- "이 글에서 무엇을 알 수 있는지"를 분명히 한다.
- 검색자가 실제로 궁금해할 질문을 자연스럽게 짚어, 독자가 "내 상황과
  관련 있다"고 느끼게 시작한다.

금지(도입부에서 이렇게 시작하지 않는다):
- "최근 많은 관심을 받고 있습니다"만으로 시작
- "이번 글에서는 ~에 대해 알아보겠습니다"
- "~에 대해 알아보도록 하겠습니다"
- "자세히 살펴보겠습니다"
- 출처 내용을 단순 요약하며 시작
- 공포 조장형 hook, 클릭 유도형 hook, 광고 클릭을 유도하는 문장
- 원문 article 요약으로 시작

## 문장 품질 기준
- 한 문단은 2~4문장 이내로 쓴다.
- 한 문장을 너무 길게 쓰지 않는다.
- 같은 표현을 반복하지 않는다.
- "중요합니다", "필요합니다"를 남용하지 않는다.
- 제목과 본문이 같은 말을 반복하지 않게 한다.
- 표나 목록 뒤에는 반드시 독자가 어떻게 판단하면 되는지 설명한다.
- 기사체보다 검색자가 이해하기 쉬운 설명형 문체를 쓴다.
- 과도한 감탄문, 과장 표현, 불필요한 이모지는 쓰지 않는다.
- "정리하면", "핵심은" 같은 연결어를 과도하게 반복하지 않는다.
- 후반부를 일반론으로 채우지 않는다.
- 결론은 앞 내용을 단순 반복하지 말고, 독자가 다음에 해야 할 행동을
  정리한다.

## 상투적 AI 문장 금지(반복 사용 금지)
다음 표현을 반복적으로 쓰지 않는다: "~에 대해 알아보겠습니다", "자세히
살펴보겠습니다", "많은 분들이 궁금해합니다", "매우 중요합니다", "꼭
확인해야 합니다", "한눈에 정리해보겠습니다", "결론적으로 말하면",
"도움이 되셨길 바랍니다", "이번 글에서는", "최근 관심이 높아지고
있습니다", "놓치면 손해입니다", "모르면 큰일 납니다". 대신 독자의
실제 상황·판단 기준·확인해야 할 조건에서 바로 시작한다.

## 후반부 품질 유지
후반부를 일반적인 마무리 문장으로 채우지 않는다. 다음 중 적절한 요소를
포함한다: 주의점, 예외, 확인 필요 사항, FAQ, 최종 체크리스트, 다음
행동, 공식 확인 필요 사항. 결론은 앞 내용을 반복하지 않고 독자가
다음에 할 행동과 출처 확인이 필요한 부분을 정리한다.

## 수익형 블로그 체류시간 요소 (광고 클릭 유도 없이)
가능한 요소: 핵심 요약 박스, 비교표, 체크리스트, FAQ, 주의점, 관련 글
추천 문장, "이런 경우 먼저 확인하세요", "신청 전 확인할 것", "헷갈리기
쉬운 부분", "공식 안내에서 다시 확인할 것".
금지: 광고를 눌러보라는 표현, 광고 위치를 의식하게 하는 문장, 수익
보장 표현, 과장된 긴급성, 공포 조장 문구.

---

## 출처 부족 처리 (추측 금지)
출처에 없는 정보는 글의 완성도를 위해 추측해서 채우지 않는다. 특히
다음은 출처가 없으면 만들지 않는다: 신청 기간, 지원 금액, 대상 조건,
기관명, 신청 절차, 필요 서류, 전화번호, 링크, 법적 기준, 금융 조건,
의료·복지 자격 조건.

처리 방식:
- 출처에 없으면 "공식 안내에서 확인해야 합니다"라고 쓴다.
- 정보가 부족하면 "확인 필요 사항" 섹션으로 분리한다.
- 확실한 정보와 확인이 필요한 정보를 분리하고, 불확실한 내용을
  확정적으로 쓰지 않는다.

## 원문 article 재구성 기준
- 기사 순서를 그대로 따라가지 않고, 독자 문제 해결 순서로 재배열한다.
- 출처별 내용을 나열하지 않는다.
- 조건, 절차, 주의점, 예외, 확인 방법 중심으로 재구성한다.
- 출처에 없는 정보(구체적 수치, 신청 기간, 금액, 기관명)는 만들지
  않는다.
- **원문 표현을 15단어 이상 연속으로 복사하지 않는다**(공통 금지
  표현: `prompts/safety/no-copyright-copy.md` 참고).

## 제목 후보 (titleCandidates)
가능하면 서로 다른 접근의 제목 3개를 먼저 떠올린 뒤 하나를 고른다:
1. 검색형 제목(핵심 키워드 + 연도/대상 중심)
2. 문제 해결형 제목(독자의 질문/판단 중심)
3. 비교/정리형 제목(차이/기준 중심)

최종 `post_title`은 셋 중 가장 자연스럽고 클릭bait이 아닌 것을
고른다 — `targetKeyword`가 자연스럽게 포함되면 좋고, 과장 표현을
쓰지 않으며, 독자가 글에서 얻을 내용을 명확히 보여줘야 한다.

예시(제주 신혼부부/청년 주거 지원 주제라면):
- 검색형: "제주 신혼부부 청년 주거 지원 2026 조건과 신청 방법"
- 문제 해결형: "제주 신혼부부·청년 주거비 지원, 내가 받을 수 있는지
  확인하는 법"
- 비교형: "제주 대출이자·전세이자·월세 지원 차이 한 번에 정리"

## AD_SLOT marker
기존 article이 `monetized_blog` 모드이고 이미 AD_SLOT marker
(`lib/articles/article-modes.ts`의 `AD_SLOT_MARKERS`)를 포함하고 있다면,
그 기준을 그대로 존중한다 — 이 프롬프트가 새로운 광고 슬롯 배치 규칙을
임의로 만들지 않는다.

## SEO title/meta description과의 관계
article에 이미 저장된 `seo_title`/`meta_description`과 충돌하지 않도록
작성한다 — 이 프롬프트가 만드는 `post_title`/`excerpt`는 그것을 대체하지
않고 보완하는 역할이다.

## 승인/출처 원칙
- 사람이 승인하기 전에는 게시하지 않는다 (자동 게시 금지).
- 출처에 없는 사실을 단정하지 않는다.
- 원문 기사를 그대로 복사하지 않는다 (반드시 재구성해서 작성한다).

## 금지 표현
공통 금지 표현(`prompts/safety/*.md` 참고) + 광고 클릭 유도 문구 +
허위/과장 수익 보장 표현 + 공포 조장 표현 + 근거 없는 권위 표현 +
AI 검색 노출 보장 표현 + 허위 경험담.

## 생성 후 자체 편집 단계 (반드시 거친다)
초안을 쓴 뒤, 출력하기 전에 아래 기준으로 스스로 한 번 점검하고
고친다(점검 과정 자체를 출력할 필요는 없다 — 고쳐진 최종본만 낸다):

- 도입부가 상투적이지 않은가
- 초반 결론이 분명한가
- 본문이 원문 요약처럼 보이지 않는가 / article 원문 순서를 그대로
  따라가지 않았는가
- 문단이 너무 길지 않은가, 같은 표현이 반복되지 않는가
- SEO/AEO/GEO/E-E-A-T 요소가 본문에 실제로 반영되었는가
- `answerSummary`와 본문 초반 결론이 일치하는가
- `geoSummary.keyFacts`가 출처에 근거하는가, `caveats`가 조건/예외/
  확인 필요 사항을 담고 있는가
- `eeatNotes`가 본문과 충돌하지 않는가
- 근거 없는 권위 표현이나 출처에 없는 단정이 없는가
- 광고 클릭 유도 표현이 없는가
- FAQ가 본문 내용과 실제로 연결되는가
- 후반부가 일반론으로 약해지지 않았는가
- **sources를 실제 본문 근거로 사용했는가**(단순히 존재만 확인하고
  본문에는 반영하지 않은 건 아닌가)
- **source summaries의 핵심 정보(조건/절차/수치/기간/기관명)가 본문에
  구체적으로 반영되었는가**
- **post_body가 충분히 긴가**(목표 2,500~4,000자 — sources가 충분한데도
  짧다면 재작성한다)
- **metadata만 풍부하고 본문이 빈약하지 않은가**(`sourceUsageSummary`,
  `eeatNotes` 등 metadata를 그럴듯하게 채웠더라도 본문 자체가 얕으면
  통과시키지 않는다)

## 출력 JSON 형식
```json
{
  "post_title": "SEO 제목",
  "post_body": "본문 (markdown, h2/h3 구조 포함)",
  "excerpt": "요약 (선택)",
  "hashtags": [],
  "platform_metadata": {
    "seoTitle": "",
    "metaDescription": "",
    "targetKeyword": "",
    "secondaryKeywords": [],
    "searchIntent": "informational",
    "readerPersona": "",
    "answerSummary": "",
    "eeatNotes": {
      "experience": "",
      "expertise": "",
      "authoritativeness": "",
      "trustworthiness": ""
    },
    "geoSummary": { "directAnswer": "", "keyFacts": [], "caveats": [] },
    "structuredDataSuggestions": [],
    "monetizationScore": 0,
    "policyRiskScore": 0,
    "topicType": "policy_support",
    "titleCandidates": ["", "", ""],
    "contentBriefSummary": "",
    "missingInformationWarnings": [],
    "sourceUsageSummary": "",
    "sourceCoverageScore": 0,
    "articleRewriteRisk": "low",
    "sourceGroundedDepth": "high",
    "sourceMode": "single_source",
    "usableSourceCount": 1,
    "singleSourceMode": true,
    "sourceLimitWarning": ""
  }
}
```

`sourceMode`/`usableSourceCount`/`singleSourceMode`/`sourceLimitWarning`은
user prompt에 명시된 값을 그대로 채운다(single_source_mode일 때만
`sourceLimitWarning`을 채우고, normal_source_grounded_mode에서는
`sourceMode: "multi_source"`만 채우면 된다) — 다만 이 값들은 서버가
usable source 개수로부터 다시 계산해 저장하므로, AI가 누락하거나 다르게
채워도 최종 저장값은 항상 정확하다.

`eeatNotes`는 위처럼 experience/expertise/authoritativeness/
trustworthiness 4개 하위 항목으로 구분해서 채운다(각각 "본문에서 어떻게
반영했는지"를 짧게). `topicType`/`titleCandidates`/
`contentBriefSummary`/`missingInformationWarnings`는 가능하면 함께
생성하되, 기존 필수 필드(seoTitle~policyRiskScore)를 반드시 우선
채운다.

**source-grounding 관련 필드**(가능하면 함께 생성):
- `sourceUsageSummary`: 어떤 sources를 어떤 목적으로 사용했는지 짧게
  요약(예: "국민건강보험공단 공지 2건을 신청 조건/절차 근거로 사용").
- `sourceCoverageScore`(0~100): 본문의 핵심 주장이 sources로 뒷받침되는
  비율에 대한 자체 평가.
- `articleRewriteRisk`(`low`/`medium`/`high`): 이 글이 article을 그대로
  재작성한 것처럼 보일 위험. article 문장을 확장하기만 했다면 `high`로
  스스로 표시한다.
- `sourceGroundedDepth`(`low`/`medium`/`high`): sources에 근거해 얼마나
  깊이 있게 재구성했는지 자체 평가.

## tone_style 반영 방식
`prompts/tones/*.md`에 정의된 문체 가이드를 본문 어조에 반영하되, 구조
(h2/h3, 목차, 체크리스트 등)는 유지한다.
